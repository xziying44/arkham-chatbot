# 卡牌查询助手

教你怎么把用户的口语化查卡需求，翻译成 `search_cards` 工具的筛选参数。

## 何时加载本技能

- **不用加载**：用户说得清楚（「查一下罗兰」「找守护者的支援卡」「有没有费用3以下的法术」）→ 直接调 search_cards。
- **该加载**：用户描述含糊、用了不规范的俗称（「找几张打击卡」「有没有反制法术」「来点便宜货」），你拿不准怎么映射 → 加载本技能看 references/enums.md 的口语→枚举映射。

## 工作流

### Step 1：从用户话里提取筛选维度

常见维度（优先级从高到低）：
1. **名字/关键词** → `query`（模糊匹配，最常用）
2. **卡牌类型** → `type`（支援卡/事件卡/技能卡/敌人卡/...）
3. **职业/阵营** → `class`（守护者/探求者/...）
4. **特性** → `trait` 或 `traits_all`/`traits_any`（道具/法术/盟友/武器/...）
5. **数值** → `cost_max`/`level_exact`/`health_min`/`attack_min` 等

### Step 2：直接调 search_cards（参数直观时）

绝大多数情况参数直观，**不用读 references**，直接调。例如：
- 「查罗兰」→ `search_cards({ query: "罗兰" })`
- 「找守护者支援卡」→ `search_cards({ class: "守护者", type: "支援卡" })`
- 「有没有费用2以下的法术」→ `search_cards({ trait: "法术", cost_max: 2 })`
- 「3级以上的事件卡」→ `search_cards({ type: "事件卡", level_min: 3 })`

### Step 3：模糊描述时读 references/enums.md

用户用了俗称或不规范说法时，**读 `references/enums.md`** 查口语→数据库标准值的映射。例如：
- 「打击卡」→ 可能指 战力 图标多 → `search_cards` 没有图标筛选，改用 trait 近义或让用户澄清
- 「便宜货」→ 可能指 cost ≤ 1 或 level = 0
- 「反制/打断」→ 可能指 快速（无直接字段）或 事件卡 + 相关正文

### Step 4：处理结果

`search_cards` 返回 ≤5 张卡 + 图片路径。按结果数决定下一步：

| 结果数 | 处理 |
|---|---|
| **0 张** | 条件太严。放宽（去掉最严格的条件）或换关键词重查；仍无则 send_message 问用户更多细节 |
| **1 张** | 很可能就是用户要的。send_message 告知 + 直接 send_image 发它的正面图（`cards-db/card_images/xxx_a.jpg`） |
| **2-5 张** | 候选多。**先用 send_message 发文字列表**让用户选（避免一次发多图刷群），用户指定后再 send_image 发那一张 |

### Step 5：发图

确定要发的卡后，调 `send_image({ filePath: "cards-db/card_images/01006_a.jpg" })`。
- 正面是 `_a`，背面是 `_b`，特殊组合面 `_a-c`
- 多张卡要发时**逐张发、且每张之间等用户确认**，不要连发刷屏

## 关键约束

- **不硬凑**：工具返回 <5 张就显示实际数量，不强行凑满
- **避免刷屏**：多张候选先发文字列表，不发多图
- **多轮/并行**：一次查不清可以多查几次（不同条件组合），或并行调多个 search_cards，综合结果再决定发哪张
- 数据库只读：你无法修改卡牌数据，只能查询

## 何时该问用户（ask_user）

用户的需求有多种合理解读时，用 `ask_user` 给选项比瞎猜好：
- 「我要张强力输出卡」→ ask_user 选职业（守护者/探求者/...）再查
- 「找张便宜卡」→ ask_user 确认是费用便宜还是等级便宜
